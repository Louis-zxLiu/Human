# 答辩提纲

## 1. 赛题定位

- 我们的系统面向智慧景区数字导览场景。
- 游客侧提供语音/文本交互、景点讲解、个性化推荐。
- 管理侧提供行为分析、推荐偏好、满意度趋势和失败样例复盘。

## 2. 为什么我们的数据设计更合理

### 核心观点

我们没有把所有比赛数据都混成一个知识库，而是做了数据分层治理。

### 三层结构

1. 景区知识层  
只存灵山胜境的景点结构化资料与讲解文档，用来回答事实题。

2. 游客行为分析层  
只存比赛方 Excel 的游客行为数据，用来做偏好分析、消费趋势、停留时长和推荐辅助。

3. 推荐生成层  
用灵山知识决定讲解路线，用行为分析决定游客偏好补充。

### 这样做的好处

- 避免跨景区统计数据污染灵山事实问答。
- 提升事实准确率。
- 让系统更容易解释给评委和用户。

## 3. 为什么统一 FACT / ANALYTICS / RECOMMEND 编排

- `FACT`：回答门票、开放时间、位置、历史、文化、亮点。
- `ANALYTICS`：回答游客偏好、消费、停留时长、满意度、热门类型。
- `RECOMMEND`：输出完整路线与讲解重点。

统一编排避免了多套问答链路同时存在导致的漂移问题。

## 4. GPS 弱信号加分项

### 现实场景

- 山区、室内展馆、复杂建筑群中 GPS 可能失效。

### 我们的做法

1. 识别用户是在问路或问位置。
2. 不直接硬答，而是主动追问附近地标。
3. 根据“大佛、梵宫、照壁、桥、坛城、寺院”等关键词做候选判断。
4. 返回“我推测您可能在 X 或 Y 附近”，并给出下一步路线建议。

### 价值

- 更贴近真实景区使用场景。
- 避免伪定位和错误导航。
- 具备清晰的答辩展示效果。

## 5. 第二批改造亮点

- 补齐灵山大佛事实知识缺口。
- 建立标准题集与回归脚本。
- 推荐结果结构化展示。
- 后台增加状态卡片、推荐标签分布和失败样例。

## 6. 可以展示的结果

- 事实问答更稳定。
- 推荐解释更完整。
- GPS 弱信号场景可演示完整多轮交互。
- 后台更能体现运营价值。

# 测试评测报告

项目名称：灵山胜境导览服务 AI 数字人系统
评测对象：文本问答、游客行为分析、路线推荐、边界拒答
评测日期：【填写评测日期】

## 1. 评测目标

本评测用于验证系统是否满足赛题对“精准景区知识问答”和“系统稳定可靠”的要求。重点关注：

- 回答是否来自正确数据源。
- DOCX 景区事实是否准确。
- 游客行为统计数值是否准确。
- 个性化路线推荐是否合理。
- 证据不足时是否拒答，避免幻觉。

## 2. 评测数据

统一评测集文件：

```text
tests/unified_eval_cases.jsonl
```

评测集规模：`1200` 题，其中 dev `900` 题、holdout `300` 题。

覆盖类型：

| 类型 | 题数 | 说明 |
| --- | ---: | --- |
| DOCX 结构化事实 | 320 | 景点位置、参数、功能、文化内涵、亮点、开放信息 |
| DOCX RAG 深度资料 | 180 | 灵山大佛、梵宫、九龙灌浴等历史文化与讲解资料 |
| 游客行为 SQL | 420 | 总量、均值、TopN、分组统计、趋势、消费、满意度、多条件组合 |
| 推荐融合 | 160 | 历史文化、风景打卡、亲子同游、建筑艺术、轻松慢游、经典首游、弱 GPS |
| 边界拒答 | 120 | 防止数据源混用、防止编造实时或无证据信息 |

## 3. 评测方法

评测集生成命令：

```bat
conda run -p "D:/Human/env" python -m app.cli generate-unified-eval --target 1200 --output tests/unified_eval_cases.jsonl
```

统一评测命令：

```bat
conda run -p "D:/Human/env" python -m app.cli eval-unified --report reports/unified_eval_report.json --markdown-report reports/unified_eval_report.md --strict --fail-under 90
```

报告输出：

```text
reports/unified_eval_report.json
reports/unified_eval_report.md
```

评分维度：

| 维度 | 分值 | 说明 |
| --- | ---: | --- |
| 路由正确 | 15 | 是否正确进入 FACT、ANALYTICS、RECOMMEND |
| 数据源正确 | 20 | 是否使用 DOCX、行为数据或推荐融合的正确来源 |
| 事实/数值命中 | 35 | 事实关键词、数值、排名、路线节点是否命中 |
| 表达完整 | 15 | 回答是否完整、可理解、包含必要解释 |
| 边界安全 | 15 | 是否拒绝无证据问题，避免编造 |

通过线：

- 总分不低于 `90`
- DOCX 事实题不低于 `90`
- 游客行为数据题不低于 `90`
- 边界题不低于 `85`

## 5. 关键测试场景

### 5.1 DOCX 景区事实问答

示例问题：

```text
灵山梵宫为什么被称为佛教艺术的卢浮宫？
```

检查点：

- 回答包含“灵山梵宫”。
- 回答包含“佛教艺术”。
- 不混入游客行为数据。

### 5.2 游客行为数据分析

示例问题：

```text
平均停留时间最长的景点是哪几个？
```

检查点：

- 路由进入 `ANALYTICS`。
- 回答明确说明“基于游客行为数据分析”。
- 排名结果与 `tourist_behavior` 表动态 SQL 结果一致。

### 5.3 路线推荐融合

示例问题：

```text
我喜欢自然风光和拍照打卡，请推荐一条适合拍照的路线，并说明为什么适合多数游客。
```

检查点：

- 路由进入 `RECOMMEND`。
- 推荐标签为“风景打卡”。
- 至少包含 3 个路线节点。
- 包含预计时长、讲解重点和游客行为依据。

### 5.4 边界拒答

示例问题：

```text
请告诉我明天实时排队多久。
```

检查点：

- 系统不编造实时排队信息。
- 明确提示需要实时运营数据。
- 给出可改问方向。

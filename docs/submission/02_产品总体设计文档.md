# 产品总体设计文档

项目名称：灵山胜境导览服务 AI 数字人系统  
赛题名称：A5-景区导览服务 AI 数字人

## 1. 项目背景

智慧景区的核心问题已经不再只是“有没有展示内容”，而是“能不能在真实场景下可靠地服务游客，并把交互沉淀成运营价值”。传统导览方式存在三个明显短板：

- 讲解内容固定，难以支持开放式问答。
- 游客行为数据难以转成可落地的管理洞察。
- 纯大模型回答容易混用数据源，事实与统计结论难以审计。

本项目的目标，是构建一套既能服务游客、又能服务景区运营、还能稳定评测与回放的 AI 数字人导览系统。

## 2. 设计目标

| 赛题要求 | 系统设计 |
| --- | --- |
| 多模态交互 | 支持文本、语音、TTS、数字人视频联动 |
| 智能问答与讲解 | 结构化景区事实 + hybrid RAG 深资料问答 |
| 个性化推荐 | route planner 生成个性化路线和讲解重点 |
| 管理后台 | 展示互动数据、知识库状态、行为分析和失败样例 |
| 工程可交付 | 统一 CLI、可重复数据构建、可部署前后端 |
| 可评测性 | 1200 题统一评测集，最新严格评测总分 `99.38/100` |

## 3. 总体架构

系统采用四层架构：

```text
游客 / 管理员
   |
   v
交互层：游客前台、登录页、管理后台、语音输入、数字人视频
   |
   v
服务层：FastAPI、会话管理、ASR/TTS、日志服务、数字人引擎
   |
   v
智能决策层：planner、structured facts、semantic SQL、hybrid RAG、route planner、response contract
   |
   v
数据层：DOCX 知识资料、SQLite 行为库、评测集、报告与日志
```

## 4. 核心设计

### 4.1 Planner-first 架构

本次升级后，系统不再依赖简单的粗粒度业务路由，而是先由 planner 生成执行计划，再交由具体 agent 执行。

planner 负责：

- 识别问题类型
- 判断所需证据类型
- 选择执行策略
- 决定是否拒答或追问
- 记录可审计计划

主要策略包括：

| 策略 | 适用场景 | 主要执行单元 |
| --- | --- | --- |
| `structured_fact` | 景区参数、位置、开放信息、明确事实 | `fact_agent.py` |
| `semantic_sql` | 访问量、停留时长、消费、满意度等统计分析 | `sql_agent.py` |
| `hybrid_rag` | 历史文化、讲解扩展、深资料问答 | `chroma_agent.py` |
| `route_planner` | 个性化路线推荐、讲解节点规划 | `recommendation_agent.py` |
| `refusal` | 实时外部数据、证据不足、越界问题 | `response_contract.py` + pipeline |

### 4.2 数据隔离设计

系统严格区分：

- 景区结构化事实
- 游客行为分析数据
- 非结构化景区深资料

这样可以保证：

- 事实问题不被行为数据污染
- 统计问题不被自由生成污染
- 深资料场景也能被证据检索约束

### 4.3 路线推荐设计

route planner 会综合：

- 用户兴趣标签
- 景区知识点
- 游客行为偏好
- 讲解重点
- 预计游览时长

输出的不是简单景点列表，而是可执行路线：

- 路线标题
- 适合原因
- 节点顺序
- 节点讲解摘要
- 时间安排
- 支撑依据

## 5. 响应契约设计

为了解决“回答能看懂，但系统不可审计”的问题，本项目引入统一 response contract。

标准字段：

- `answer`
- `response_kind`
- `plan`
- `evidence`
- `refusal`
- `warnings`
- `observability`

这套契约同时服务于：

- 前台展示
- 后台回放
- 失败样例分析
- 自动化评测
- 后续线上观测

## 8. 前台与后台设计

### 8.1 游客前台

- 视频主位布局，聊天区与数字人舞台分离。
- 支持文本、语音、路线卡片、弱 GPS 问路。
- 历史会话按用户隔离。

### 8.2 管理后台

- 数据驾驶舱展示互动量、意图分布、满意度趋势、热点问题。
- 知识库面板展示 DOCX 与行为库状态。
- 失败样例面板用于查看拒答、回退与错误案例。
- 评测面板直接呈现统一评测结果。

## 9. 安全边界

系统明确拒绝以下内容的伪造回答：

- 实时票价
- 实时排队时间
- 实时停车位
- 未录入演出安排
- 缺乏证据的景区事实

拒答不仅是自然语言说明，还会生成机器可读 `refusal.reason`。

## 11. 创新点

### 11.1 Planner-first 真实链路

不是把所有问题都丢给同一种 RAG，而是先规划再执行。

### 11.2 RAG 与 SQL 的职责分离

统计问题交给 SQL，景区知识交给事实层和 RAG，避免混源。

### 11.3 统一响应契约

让回答不仅“能看”，还“能追、能测、能回放”。

### 11.4 可观测日志

日志直接保留计划、证据、拒答和回退信息，便于真实生产场景排障。

## 12. 结论

当前系统已经具备完整产品形态与工程闭环：

- 面向游客，有自然交互、事实问答、深资料讲解、路线推荐和数字人联动。
- 面向景区，有可用后台、结构化日志、知识库状态和统一评测。
- 面向真实场景，有 planner-first 决策、semantic SQL 统计、机器可读拒答和 `99.38/100` 的统一评测结果。
